⚔️ Shadow OS — Complete Manual

A capability-first cognitive engine that turns a request into a ratified deliverable.

This manual explains, in plain language, what Shadow OS can do and exactly how to use it — from a one-line offline run to driving the 7-shadow fleet on a real Claude model with durable memory. No prior context needed.

What it is

Shadow OS takes a directive ("tighten this proposal", "research why retention dropped") and runs it through a team of seven specialists — called shadows — coordinated by an orchestrator named Monarch. It returns a finished answer only after that answer passes a quality gate.

In plain words: think of it as a small, opinionated agency. You hand in a brief. A manager (Monarch) figures out what you really asked for, picks the right specialists, runs them in order, makes each one's output feed the next, and refuses to ship anything that fails review. You get back the polished result plus a full record of how it was made.

Three things make it distinctive:

  • Capability-first. The shadows are defined by what they can do (compress, analyze, write…), not by personas. Their behaviour is data you can edit.
  • One loop, many specialists. Every shadow runs the same four mental steps; only their focus differs.
  • Nothing ships unratified. A single gate (Thresher) has veto power over every output.

Install & your first run

Python 3.10 or 3.11. No required dependencies — it runs fully offline out of the box.

# from the repo root
# (optional) create a virtualenv first
pip install -e .

# run the engine offline — no API key needed
python -m shadow_os.cli "tighten this bloated proposal deck"

That prints the routed loadout and the (mock) result. To see real reasoning, jump to With Claude.

Why offline works: the reasoning step is model-agnostic. With no model wired in, it uses a deterministic MockLLM so you can exercise routing, gating, memory, and the kernel without a key or network. Swap in Claude when you want real output.

The three layers

The codebase is three packages, stacked. You can use just the top, or all three.

shadow_os/
Cognitive layer — the engine
Monarch + the 7 shadows. Decides which specialist reasons about what. This is what you usually call.
▼ optionally runs on
kernel/
Resource layer — the AIOS-style kernel
Decides which request gets the model, memory, and tools. Shared model with usage accounting, durable storage, per-agent permissions.
▼ reuses primitives from
monarch/
Primitives — Monarch OS v1.1
The original single-agent pipeline. Its compressor (Caveman), QA checks, and the model interface are reused by the engine, not duplicated.
In plain words: the engine is the brain; the kernel is the operating system it can run on (giving it durable memory, shared compute, and security); the primitives are the reusable parts both lean on. For most uses you only touch the engine.

The 4-stage loop — how a shadow thinks

Every shadow runs the same four steps, looping until its reasoning says the goal is met (Monarch can stop it).

STAGE 1

Perception

Take in the directive (or the previous shadow's output), strip noise, normalize it.

→
STAGE 2

Memory

Recall relevant prior context for this kind of task.

→
STAGE 3

Reasoning

Plan, self-critique, score its own confidence. This is the step that calls the model.

→
STAGE 4

Action

Produce the artifact + a small "what I learned" upgrade note (dual output).

Only Stage 3 needs a model. Perception, Memory, and Action are deterministic code. That's why the engine is testable and fast offline — the model is one swappable piece, not the whole machine.

How a full run flows (Monarch)

  1. Reconstruct. Strip the polite surface of your request down to the real intent; judge stakes (System 1 = quick, System 2 = deliberate).
  2. Classify. A fast regex decides the task class (compression, research, commercial, architecture, artifact, redirection) — no model call, zero cost.
  3. Route a loadout. Look up which shadows handle that class (and reuse a previously winning team from memory if there is one).
  4. Sequence. Run each shadow's loop in order; each one's output becomes the next one's input.
  5. Ratify. Thresher's gate inspects the final artifact. Pass → ship. Fail → veto, nothing ships.
  6. Learn & log. Record the winning loadout, emit the upgrade note, and deposit the result into memory (compressed first).

Routing & loadouts — say this, get that

Routing is deterministic and inspectable. Phrase your directive with these cues and you'll hit the matching team:

Capabilities · the 7 shadows in depth

Each shadow is configured by data: a list of capabilities, the triggers that route to it, and guardrails (its failure mode, neutralized). Here is the full roster.

👑 Monarch

Sovereign · orchestrator

Not a worker — the conductor. Reconstructs intent, routes the loadout, sequences the loops, arbitrates conflicts, and holds the final veto. Nothing ships without Monarch's ratification.

Owns
  • Sovereign Reconstruction (intent → beliefs → System-1/2 calibration → signal-to-noise)
  • Classification, routing, sequencing
  • Ratification, governance log, telemetry, memory deposit

Thresher

Grandmaster · the gate

The critical-reasoning gate. Everything external passes through it. It compresses to the essential signal and holds the release gate — the one check that can approve or veto a ship.

Capabilities
  • Signal compression & brief/RFP deconstruction
  • Solution-gap analysis (stated vs delivered)
  • Risk modeling & pre-mortem
  • Release-gate QA (the veto), Socratic interrogation
Guardrail
  • "The Deleter" under stress — it must run full impact analysis before any cut, so it doesn't destroy essential nuance.
What its gate actually checks
  • Not empty · no forbidden register or exclamation marks · no unresolved markers (TODO, ??) · above a minimum signal length.

Aegis

Grandmaster · commercial & standards

Turns architecture into priced, winnable commercial outcomes, and installs reusable standards. Runs every job through a Commercial Triage Matrix first (TRANSFORM / AMPLIFY / AVOID / AUTOMATE).

Capabilities
  • Proposal & commercial engineering, margin architecture
  • Revenue sensing, stakeholder priority mapping
  • IP/framework architecture, standards install
Guardrail
  • Encode standards as reusable templates, not personal heroics — its endgame is making itself unnecessary.

Axiom

Master · architecture

First-principles deconstruction and system/program design. Produces structural blueprints, not prose.

Capabilities
  • First-principles problem deconstruction
  • System & program architecture, competency design
  • Second-order reasoning, coherence pruning
Guardrail
  • Owns architecture; hands content production to Quill — a clean boundary, no overlap.

Analyst

Master · evidence

The evidence spine. Grounds claims so the gate and real audiences can't reject them.

Capabilities
  • Data analysis & contradiction scanning
  • Evidence-chain construction, pattern detection
  • Source verification & provenance
Guardrail
  • Builds the evidence; never ratifies its own work — Thresher/Aegis test it.

Quill

Master · artifact production

The surface the audience actually sees — executive writing, documents, decks, learning content. Nothing ships as a raw thought.

Capabilities
  • Executive writing & thought leadership
  • Logic-chain construction & verification
  • Documentation, learning content
Guardrail
  • Produces content only after architecture is set (Axiom owns the design).

Ira

Grandmaster-Sovereign · personal-only

The only shadow that works on you, not the problem — approach redirection. Its success signal is "did the person become more able to guide themselves?" Its Stillness Gate ships wisdom (the class of problem), never quick advice.

Capabilities
  • Reframe-before-react, cross-domain synthesis
  • Motivation-architecture matching
  • Temporal grounding (one present-tense next action)
Guardrail
  • Cannot produce technical artifacts; defers to human support in genuine crisis.
Access-gated. Ira never enters a team unless you pass context={"personal": True} (CLI: --personal). If routing picks Ira but the run isn't personal, Monarch governs the task itself instead.

Capabilities · the kernel (resource layer)

Optional. When you give Monarch a kernel, the fleet runs on it: the model is shared and metered, each shadow is access-checked, loop state is snapshotted, and shipped output is persisted.

ManagerWhat it doesModule
LLM CoreOne shared model across all shadows, with call + token accountingllm_core.py
SchedulerRuns dispatched jobs in priority order (lowest number first)scheduler.py
Context ManagerDeep snapshot / restore of a shadow's loop state on a context-switchcontext.py
Storage + MemoryDurable, atomic-write key-value store + LRU memory with searchstorage.py
Tool ManagerA registry of tools; every call is permission-checked firsttools.py
Access ManagerPer-agent permissions; denies what isn't grantedaccess.py
Concrete example baked in: the commercial agent (Aegis) is granted access to "pipeline data"; the personal agent (Ira) is not. Ask the kernel to run that tool as Ira and it raises AccessDenied. Security is enforced at the resource boundary, independent of what the engine decides to attempt.

Capabilities · memory (disk, Notion, embeddings)

The kernel's memory is durable and pluggable.

  • Disk (default). Give the kernel a storage_path and every write flushes to disk atomically (crash-safe). A fresh kernel on the same path rehydrates its memory.
  • Notion (optional). Swap the backend for NotionStorage and memory lives in a Notion database — browsable and editable in the same workspace as your specs.
  • Search. Token-overlap by default (no dependencies); pass an embedder for true semantic search by meaning. HashEmbedder works offline; VoyageEmbedder gives real embeddings with a key.
Going live with Notion + embeddings needs three things: a Notion integration token (NOTION_TOKEN), a database with Key (title) and Payload (rich_text) properties, and VOYAGE_API_KEY for real semantics. Without them, disk + token-overlap search work unchanged.

Capabilities · model tiering (Sonnet + Haiku)

The Claude adapter picks the model to fit the task:

TaskModelSettings
Normal / deliberate work (default)Sonnet 4.6 claude-sonnet-4-6adaptive thinking, effort: high
Clear, simple promptsHaiku 4.5 claude-haiku-4-5fast — no thinking/effort (Haiku doesn't accept them)

"Clear" = a short prompt with no complexity markers (design, analyze, strategy, risk, why, decide…). Turn tiering off to pin one model with auto_tier=False, or set your own with model= / simple_model=.

Prompt caching is on. Each shadow's system prompt is stable, so it's sent as a cached block — repeated calls reuse the cached prefix and cost less. Per-model usage is tracked on llm.usage["by_model"].

The 8 governing laws

  1. Capability-first — no persona survives as a standalone entity; capabilities are the unit.
  2. No mixed justification — each capability earns its place on its own evidence.
  3. Evidence-grounded — survival is decided by real usage, not self-report.
  4. Fold or retire — a capability that can't stand alone is folded in or removed; no bloat.
  5. Import the function, not the pathology — every borrowed strength ships with its failure mode neutralized as a guardrail.
  6. RSI dual-output — every run yields a deliverable plus an upgrade note.
  7. Monarch absolute — no output ships unratified.
  8. Compression-before-deposit — nothing bloated enters memory.

Laws 6, 7, and 8 are enforced in code and covered by tests; the rest are design discipline encoded in how the fleet is built.

from shadow_os import Monarch

monarch = Monarch()                      # offline MockLLM by default
task = monarch.run("tighten this bloated proposal deck")

print(task.final_output)   # the ratified result
print(task.trace())        # task_class, loadout, gamma, RSI, governance

Run the bundled tour across five task classes:

python examples/run_engine.py

Using it · with a real Claude model

# install the SDK and set a key
pip install -e ".[claude]"
export ANTHROPIC_API_KEY=sk-ant-...

python examples/run_with_claude.py "draft the Hexaware proposal summary"
from shadow_os import Monarch
from monarch.claude_llm import ClaudeLLM

monarch = Monarch(llm=ClaudeLLM())       # Sonnet 4.6 default, Haiku for clear tasks
task = monarch.run("research why retention dropped after onboarding")
print(task.final_output)
print(llm.usage)  # once you keep a reference: llm = ClaudeLLM(); ...

Tune it:

ClaudeLLM(
    model="claude-sonnet-4-6",      # default tier
    simple_model="claude-haiku-4-5", # clear-task tier
    auto_tier=True,                  # False = always use `model`
    effort="high",                   # low | medium | high
    max_tokens=16000,
)

Any other provider works too — pass anything with complete(system, user) -> str:

from monarch import Monarch, CallableLLM
monarch = Monarch(llm=CallableLLM(lambda system, user: my_model(system, user)))

Using it · on the kernel (durable + metered)

from kernel import Kernel
from shadow_os import Monarch

kernel = Kernel(storage_path="state.json")   # durable memory on disk
monarch = Monarch(kernel=kernel)               # boots the fleet onto the kernel
task = monarch.run("draft the proposal summary")

kernel.llm_core.usage()    # {'calls': 3, ...} shared + accounted
len(kernel.memory)         # shipped output persisted

# a fresh kernel on the same path resumes the memory
kernel2 = Kernel(storage_path="state.json")
kernel2.memory.search("retention drop")   # [(key, record, score), ...]

Notion-backed memory with semantic search:

from kernel import Kernel, NotionStorage, HttpNotionTransport, VoyageEmbedder
from shadow_os import Monarch

kernel = Kernel(
    storage=NotionStorage("YOUR_DATABASE_ID", HttpNotionTransport()),  # NOTION_TOKEN env
    embedder=VoyageEmbedder(),                                          # VOYAGE_API_KEY env
)
Monarch(kernel=kernel).run("research why retention dropped")

Using it · command line

# engine
python -m shadow_os.cli "research why retention dropped" --trace
python -m shadow_os.cli --personal "I'm stuck on how to approach the launch"

# the v1.1 single-agent pipeline (Caveman/QA)

  • Exit code is 0 when the output shipped, 1 when the gate vetoed it.

Reading the result (the Task object)

Every run returns a Task. The useful fields:

task.final_output
the ratified text (empty string if vetoed)
task.shipped
True only if Thresher's gate passed
task.task_class
the routed class (e.g. commercial)
task.shadow_loadout
the team that ran, in order
task.gamma
system1 (quick) or system2 (deliberate)
task.results
per-shadow output, confidence, self-critique
task.rsi_artifacts
the "what improved" upgrade notes (one per shadow)
task.governance_log
every step + whether Monarch ratified it
task.trace()
a compact dict of all the above — best for logging
If shipped is False: the gate vetoed the output. Check task.governance_log for the VETO line — it names the failing checks (empty, forbidden register, unresolved markers, or below minimum signal).

Extending it

Add a routing rule

Edit shadow_os/router.py: add a regex to _CLASS_RULES and a team to _DISPATCH.

Tune a shadow

Shadows are data. In shadow_os/shadows/<name>.py edit the capabilities, deployment_triggers, guardrails, and reasoning_directive — no new class needed.

Harden the gate

Add checks to Thresher.gate() in shadow_os/shadows/thresher.py. Anything it flags blocks the ship.

Register a kernel tool with a permission

kernel.tools.register("send_email", send_fn, permission="comms:send")
kernel.access.grant("quill", "comms:send")
kernel.syscall("quill", "tool.call", tool="send_email", ...)  # denied for others

FAQ & troubleshooting

Is this AIOS?

No. Shadow OS is the cognitive/agent layer; AIOS is a kernel/resource layer. The included kernel/ is an AIOS-style resource tier the engine can run on — but it's a thin, app-specific slice, not the full AIOS project.

Why was my output vetoed?

Thresher's gate rejects empty output, forbidden register words, exclamation marks, unresolved markers (TODO, ??), or text below a minimum length. The governance log names the exact failure.

Why did a simple task go to Haiku?

The Claude adapter tiers by the prompt text. Short, marker-free prompts route to Haiku for speed. Set auto_tier=False to always use Sonnet (or your chosen model).

Do I need an API key?

No — the engine runs fully offline on MockLLM. A key is only needed for real reasoning via ClaudeLLM.

Does memory survive a restart?

Yes, when you give the kernel a storage_path (or a Notion backend). Without one, memory is in-process and resets each run.

The kernel raised AccessDenied.

That's the Access Manager working. Grant the permission with kernel.access.grant(agent_id, permission) (booting the fleet grants the defaults automatically).
